# 05. 同梱ワークフロー解説

本リポジトリには5つの Agentic Workflow が同梱されています。すべて **Copilot エンジン**で動作します（モデルは [references/model-policy.md](references/model-policy.md)）。

| ワークフロー | ファイル | トリガー | 既定モデル |
|-------------|---------|---------|-----------|
| PR AI レビュー | [.github/workflows/pr-ai-review.md](../.github/workflows/pr-ai-review.md) | 手動（workflow_dispatch） | 選択（既定 Sonnet 4.6） |
| README 自動更新 | [.github/workflows/auto-readme-update.md](../.github/workflows/auto-readme-update.md) | push（main） | Sonnet 4.6 |
| Issue トリアージ | [.github/workflows/issue-triage.md](../.github/workflows/issue-triage.md) | issues（opened/reopened） | Sonnet 4.6 |
| CI Doctor | [.github/workflows/ci-doctor.md](../.github/workflows/ci-doctor.md) | workflow_run（失敗時） | GPT-5.3 Codex |
| Daily レポート | [.github/workflows/daily-report.md](../.github/workflows/daily-report.md) | schedule（平日朝） | Haiku 4.5 |

---

## 1. PR AI レビュー（pr-ai-review）

### 何をするか

手動ディスパッチで **PR 番号・AI モデル・最大レビュー回数** を指定すると、選んだモデルがその PR をレビューし、結果を **1件のコメント**として投稿します。

### 運用フロー

```
PR 発行
  └▶ ① ディスパッチ → AI レビュー(1回目)  → ラベル ai-review-1
        └▶ 人間が修正・コミット・プッシュ
              └▶ ② ディスパッチ → AI レビュー(2回目) → ラベル ai-review-2
                    └▶ 人間が修正・コミット・プッシュ
                          └▶ ③ ディスパッチ → AI レビュー(3回目) → ラベル ai-review-3
                                └▶ 規定回数到達 → AI レビュー完了
                                      └▶ 人間の最終確認へ
```

### 入力パラメータ

| 入力 | 型 | 既定 | 説明 |
|------|----|------|------|
| `pr_number` | string | （必須） | レビュー対象の PR 番号 |
| `model` | choice | `claude-sonnet-4.6` | `claude-sonnet-4.6` / `gpt-5.4` / `gpt-5.3-codex` / `claude-haiku-4.5` |
| `max_reviews` | choice | `3` | レビューの最大回数（1〜3） |

### 設計のポイント（要件との対応）

| 要件 | 実装方法 |
|------|---------|
| 選択肢から AI モデルを指定 | `workflow_dispatch` の `model` を `type: choice` で定義し、`engine.model: ${{ github.event.inputs.model }}` に渡す |
| レビュー回数をカウント（既定3回） | PR ラベル `ai-review-1/2/3` で回数を永続化。Step 1 で現在ラベルから今回の回数 N を判定 |
| 規定回数で完了 | N が `max_reviews` に達したらコメントで「AI レビュー完了 → 人間の最終確認へ」と宣言。次回ディスパッチは Step 1 で完了判定されスキップ |
| 同一観点で再レビュー（観点を増やさない） | 「固定レビュー観点」の5項目だけを毎回使用。新カテゴリ追加を本文で明確に禁止 |
| 指摘を収束させる | 2回目以降は前回の AI コメントを読み戻し、解消済みは消す／水増ししない。回ごとに件数が減る |
| 本質的な指摘を残す | 枝葉（Minor）は解消されれば再掲せず、Critical/Major を前面に残す |

### なぜ「コメント＋ラベル」で状態を持つのか

gh-aw のワークフローは実行のたびにまっさらな状態で起動します。回数や前回指摘を覚えておくには GitHub 上の永続データが必要です。

- **ラベル** = 回数カウンタ（`ai-review-N`）。軽量で一目で分かる。
- **過去のレビューコメント** = 前回指摘の記憶。読み戻して比較に使う。

この2つの組み合わせで、外部 DB なしに「同一観点・件数収束・規定回数完了」を実現しています。

### 使い方

```bash
# CLI から
gh workflow run "PR AI Review" \
  -f pr_number=42 \
  -f model=claude-sonnet-4.6 \
  -f max_reviews=3
```

または **Actions タブ → PR AI Review → Run workflow** から入力して実行。

> 💡 モデル選びの目安: 通常は `claude-sonnet-4.6`（バランス）/ `gpt-5.4`（汎用）、コード中心の重い PR は `gpt-5.3-codex`、軽量チェックは `claude-haiku-4.5`（高速・低コスト）。詳細は [references/model-policy.md](references/model-policy.md)。

## 2. README 自動更新（auto-readme-update）

### 何をするか

`main` への push でファイルが変わると、変更内容を解析し、**既存 README の書き方・粒度に合わせて** README を更新する **PR を作成**します。

### 設計のポイント

| 要件 | 実装方法 |
|------|---------|
| ファイル更新で自動起動 | `on: push: branches: [main]`。`docs/`・`*.lock.yml`・skills は `paths-ignore` で除外 |
| 内容に応じた適切な粒度 | 変更を分類し、README 反映が必要な変更だけを最小差分で反映 |
| 既存 README の書き方に合わせる | Step 2 で既存 README を読み、言語・トーン・見出し構成・粒度・体裁を学習してから更新 |
| 安全に更新 | 直接 push せず `create-pull-request` で PR 提案。人間がレビューしてマージ |
| 過剰更新を防ぐ | 内部実装・テストのみの変更など README に無関係なら何もしない |

### 注意点

- 無限ループ防止のため、README 更新 PR 自体やドキュメント変更では再トリガーしないよう `paths-ignore` を設定しています。
- このワークフローは PR を作るだけです。マージは人間が行います。

## 3. Issue トリアージ（issue-triage）

### 何をするか

Issue が**開かれた/再オープンされた**ら、内容を分析して**既存ラベル体系に沿ったラベルを自動付与**します。情報不足なら確認コメントを残します。

### 設計のポイント

| 要件 | 実装方法 |
|------|---------|
| 開いたら自動起動 | `on: issues: types: [opened, reopened]`（手動実行も可） |
| 既存ラベルを尊重 | `add-labels` の `allowed` パターンにあるラベルだけ付与（勝手に新規作成しない） |
| 過剰ラベルを防ぐ | `max: 3`。断定できないものは付けない |
| 情報不足のフォロー | `add-comment` で1件だけ、不足情報を丁寧に確認 |

## 4. CI Doctor（ci-doctor）

### 何をするか

CI/ビルドのワークフローが**失敗**したら、ログを調べて**原因と修正方針を Issue で報告**します。コード調査に強い **GPT-5.3 Codex** を既定にしています。

### 設計のポイント

| 要件 | 実装方法 |
|------|---------|
| 失敗時に自動起動 | `on: workflow_run: types: [completed]` + `branches: [main]`。本文で `conclusion == failure` 以外は早期終了 |
| ノイズ防止 | 失敗以外では Issue を作らない。`[ci-doctor]` の重複 Issue を量産しない |
| 原因特定 | ジョブ・ステップ・失敗ログと該当コミットを照合 |
| コード調査向きモデル | 既定 `gpt-5.3-codex` |

> 💡 `workflow_run` は**セキュリティと性能のため `branches` 制限を付けるのが推奨**です（全ブランチで走らないように）。

## 5. Daily レポート（daily-report）

### 何をするか

**平日の朝**に、直近の Issue/PR/ブロッカーを要約した**前向きな日次レポート Issue**を作成します。定型処理のため軽量・低コストな **Haiku 4.5** を既定にしています。

### 設計のポイント

| 要件 | 実装方法 |
|------|---------|
| 定時起動 | `on: schedule: cron: "0 0 * * 1-5"`（平日 9:00 JST）。手動実行で日数指定も可 |
| 安価に回す | 既定 `claude-haiku-4.5` |
| 一時的な成果物 | `create-issue` に `expires: 14`（古いレポートは自動メンテで整理対象） |
| 水増ししない | 動きが無い日は無理に内容を作らない |

> 💡 `expires` 付きの safe-output を使うと、gh-aw が自動で**メンテナンスワークフロー**（`agentics-maintenance.yml`）を生成し、期限切れの後始末を定期実行します（詳細は [06-トラブルシューティング.md](06-トラブルシューティング.md)）。

## コンパイルとコミット

どのワークフローも、編集したら必ずコンパイルし、`.md` と `.lock.yml` を両方コミットします。

```bash
gh aw compile
git add .github/workflows/*.md .github/workflows/*.lock.yml .github/workflows/agentics-maintenance.yml
git commit -m "Add/update agentic workflows"
git push
```

> ⚠️ `gh aw compile` は git リポジトリ内で実行します。新規シークレットを使う場合は `--approve` が必要です（[06-トラブルシューティング.md](06-トラブルシューティング.md) 参照）。`.lock.yml` は `gh aw compile` を実行した環境で生成してコミットしてください。
